# Репликация и консистентность

Репликация хранит копии данных на нескольких узлах. Разберём, как кворумы связывают доступность, задержку ответа и гарантии чтения.

## Кворум чтения и записи

Пусть $N$ — число реплик, $W$ — число подтверждений записи, $R$ — число ответов при чтении. Кворумы пересекаются, если:

$$
R + W > N, \qquad W > \frac{N}{2}
$$

При $N=3$ и $R=W=2$ любой кворум чтения пересечётся с кворумом записи. Для выбора актуальной версии всё ещё нужен порядок версий; одного пересечения недостаточно для линеаризуемости.

| Конфигурация | Чтение | Запись | Компромисс |
| --- | --- | --- | --- |
| $R=1,\ W=3$ | Одна реплика | Все реплики | Быстрое чтение, чувствительность к отказу |
| $R=2,\ W=2$ | Большинство | Большинство | Работа при отказе одного узла |
| $R=3,\ W=1$ | Все реплики | Одна реплика | Быстрая запись, медленное чтение |

## Запись в реплицированный журнал

Лидер присваивает записи индекс и отправляет её репликам. Ответ клиенту зависит от выбранного числа подтверждений.

```python
def replicate(entry, replicas, quorum):
    acknowledgements = 1  # запись на лидере
    for replica in replicas:
        if replica.append(entry):
            acknowledgements += 1
        if acknowledgements >= quorum:
            return "committed"
    raise TimeoutError("quorum unavailable")
```

Это учебный псевдокод: настоящий протокол должен учитывать эпохи лидера, сбои сети и повторную отправку.

### Порядок подтверждений

1. Лидер сохраняет запись в локальном журнале.
2. Реплики подтверждают устойчивое сохранение.
3. После достижения кворума лидер фиксирует запись и отвечает клиенту.

> **Важно:** получение сообщения и сохранение на диск — разные события. Гарантия сохранности определяется моментом подтверждения.

### Повторные запросы

Клиент может не получить ответ уже после фиксации записи. Повторная отправка должна использовать тот же идентификатор операции, чтобы не применить изменение дважды.

## Модели консистентности

**Линеаризуемость** сохраняет порядок неперекрывающихся операций в реальном времени. **Последовательная консистентность** сохраняет порядок операций каждого клиента. **Eventual consistency** обещает сходимость реплик после прекращения изменений.

### Пример отстающей реплики

Клиент записывает `balance = 120`, получает ответ от лидера, затем читает с реплики и видит `balance = 100`. Для read-your-writes нужен дополнительный механизм: чтение с лидера, версия сессии или ожидание нужного индекса журнала.

## Отказы и восстановление

При потере лидера новый лидер должен содержать все зафиксированные записи. Пересечение большинства помогает выбрать такой журнал, но не заменяет протокол выборов.

- **Сетевое разделение:** меньшинство не подтверждает новые записи.
- **Перезапуск узла:** восстановление по журналу и снимку состояния.
- **Отставание реплики:** догрузка пропущенных записей или свежего снимка.
